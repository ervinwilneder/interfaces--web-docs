# Extensions

The core holds what every organization has. Everything else a system
keeps (a CRM's pipelines and deals, a data platform's notebooks and
wikis, an ERP's invoices, a BI tool's dashboards) travels as an
extension: a folder under `extensions/`, named after the system's
namespace.

Anyone can write an extension, for any system, without asking the spec:
`extensions/tango/` for an ERP, `extensions/powerbi/` for dashboards.

## `EXTENSION.md`

Every extension starts with its manifest:

```yaml filename="extensions/data/EXTENSION.md"
---
type: Extension
name: data
system: nicetry data
format: data-export/1
spec: https://data-mesk.onrender.com/llms.txt
---
The notebooks and wikis of the business, as the nicetry data engine exports them (its own format, `data.md` is its manifest).
```

| Field | Required | Notes |
|---|---|---|
| `type` | Yes | Always `Extension`. |
| `name` | Yes | The namespace, the same as the folder. It is listed in the bundle's [manifest](/format/manifest) under `extensions`. |
| `system` | Yes | The system that produced it. |
| `format` | Yes | The format of its contents, as that system names it (`data-export/1`). |
| `spec` | No | A link to the documentation of that format. |

## Inside an extension

An extension follows the same rules as the core: Markdown with YAML
frontmatter, `type` always present, empty fields left out, identity by
folder, relations as paths, access state left out. Beyond that, its
layout is its system's.

Its types carry its namespace, so a document says which system it
belongs to wherever it ends up. A type without a dot is a core type; a
type with one belongs to the extension named before the dot. The data
extension writes its notebooks and wikis this way:

```yaml filename="extensions/data/notebooks/reunion-semanal/NOTEBOOK.md"
---
type: data.notebook
title: Reunión semanal
name: reunion-semanal
tags:
  - equipo
created_at: 2026-10-18T15:35:05.253Z
updated_at: 2026-10-18T15:35:05.253Z
created_by: user:equipo@acme.example
updated_by: user:equipo@acme.example
---
Lo que se decide en la reunión de los lunes.
```

```yaml filename="extensions/data/notebooks/reunion-semanal/note/001-note.md"
---
type: data.note
occurred_at: 2026-10-18T15:35:05.275Z
created_at: 2026-10-18T15:35:05.272Z
updated_at: 2026-10-18T15:35:05.272Z
created_by: user:equipo@acme.example
updated_by: user:equipo@acme.example
---
Prioridad del trimestre: consultas de empresas. Se mide con el OKR del trimestre.
```

```yaml filename="extensions/data/wikis/manual-de-ventas/WIKI.md"
---
type: data.wiki
title: Manual de ventas
name: manual-de-ventas
created_at: 2026-10-18T15:35:05.282Z
updated_at: 2026-10-18T15:35:05.300Z
created_by: user:equipo@acme.example
updated_by: user:equipo@acme.example
---
Cómo vende Acme.
```

```yaml filename="extensions/data/wikis/manual-de-ventas/page/001-como-cotizar.md"
---
type: data.page
summary: Los pasos de una cotización.
title: Cómo cotizar
created_at: 2026-10-18T15:35:05.292Z
updated_at: 2026-10-18T15:35:05.292Z
created_by: user:equipo@acme.example
updated_by: user:equipo@acme.example
---
Confirmá productos y cantidades, usá la lista de precios vigente y agendá el seguimiento.
```

Its own manifest, `data.md`, is a `data.Export` dated by the `as_of` of
its content (its last commit, never the export), and it describes its
types in `structure/` as `data.Type`, `data.Subtype` and `data.Family`
documents. An annotation inside an extension has the same shape as in
the core:

```yaml filename="extensions/data/wikis/manual-de-ventas/annotations/1.md"
---
type: Annotation
---
Actualizar cuando cambie la lista de precios.
``` An extension can describe its own types (their fields, what each
one means) in documents of its own, so that a reader understands them
without knowing the system. An extension can carry binary files too.

## References

Inside an extension, paths are relative to its folder. To point outside
it, at the core or at another extension, an extension writes a path from
the root of the bundle with a leading `/`: `/roles/ventas/vendedor`,
`/extensions/data/wikis/manual-de-ventas`. The core points into an extension
through its folder, `extensions/<system>/…`. A reader resolves a path
that starts with `/` against the root of the bundle. See
[Paths across the bundle](/format/documents#paths-across-the-bundle).

Toward the core, an extension names a piece by its folder:
`/roles/<team>/<slug>`, `/routines/<slug>`, `/policies/<slug>`. What
belongs to another system and has no path in the bundle is named by its
natural key (a WhatsApp number by its phone in E.164), never by an id.

## A whole bundle

A bundle can carry the core and the extensions of several systems at
once: one POF for the whole organization. Each system imports its own
part, `extensions/<system>/`, and resolves every `/…` against the root
of the bundle. A path that is not in the bundle is rejected, naming the
file and the path.

An extension can also travel on its own, as its system's zip, without
the rest of the bundle. Then its `/…` paths are kept as they are,
unchecked, since what they point to is not there.

An extension leaves out what can be rebuilt: a cache is not exported.

## History

An extension can keep its own history, in its own folder: its
`COMMITS.md` and a `HISTORY.md` per document. The data extension writes
it with the shape of the [core's](/format/history): the fields of its
files (`name`, `title`, `record`), its types with their namespace, and
everything named by a path relative to its folder:

```yaml filename="extensions/data/wikis/manual-de-ventas/HISTORY.md"
---
type: History
changes:
  - at: 2026-10-18T15:35:05.292Z
    commit: 34aa662c-ec2f-45cd-ab7e-483f7dbf7ac2
    action: create
    entity: subentity
    target: page/001-como-cotizar
    diff:
      body:
        from: null
        to: Confirmá productos y cantidades, usá la lista de precios vigente y agendá el seguimiento.
      summary:
        from: null
        to: Los pasos de una cotización.
      title:
        from: null
        to: Cómo cotizar
      record:
        from: null
        to: wikis/manual-de-ventas
      type:
        from: null
        to: data.page
---
```

What is gone from the extension goes to the `HISTORY.md` at the root of
its folder (`extensions/data/HISTORY.md`), named by its last path inside
the extension, or by its name, and its type.

<Callout type="info">
  **Readers keep what they do not know.** A reader that does not know an
  extension keeps it intact: it neither drops it nor rewrites it. An
  importer takes the core and the extensions it knows how to read, and
  leaves the rest as it found it.
</Callout>
